# Handoff — Workplace classification rolled out to all 20 sites + POC report finalized; next: design the "tool" vision

## TL;DR

Everything from the last handoff (`docs/handoff-202609280946.md`, Epic 6 / scraper adapters) is
done and unrelated to this session. This session's arc: the user found the resume-matcher
POC report's "Remote" column was wrong (a real Djinni posting in Ukraine, genuinely fully
remote, showed "No"). Root cause: the report layer was guessing from title/location text
because the scraper never captured a real workplace signal. Fix, done properly: added a
`Workplace` field (mutually-exclusive Fully Remote / Hybrid / On-site) to **all 20** site
adapters, plus raw HTML/JSON storage per posting (on by default, pipeline-wide) so future
fields can be re-extracted without re-scraping. Rolled out via 19 parallel-ish Haiku
subagents (2-at-a-time, per explicit user correction), each independently investigating
their site's actual page structure — not a copy-pasted heuristic. Found and fixed two
pre-existing (not introduced today) scraper pipeline bugs along the way. Did a full fresh
rescrape (1078 postings, 378 with an explicit Workplace value). Regenerated the
resume-matcher POC report against the fresh data. Then the user pointed back at the
**exact original bug case** and it still wasn't fixed — djinni's fix only covered a
title-suffix pattern, and this posting's real signal was a different structured field.
Fixed that specifically, re-verified end-to-end: the original posting now correctly reads
"Fully Remote" in the final report. Nothing in either repo is committed yet. User's
explicit next-session focus: **flesh out a "tool" vision** (CRUD of resumes, resume
metadata, transferable-skills lists, per-resume match tracking) that so far exists only as
a one-line sketch from early in this session — no UI, hosting, or architecture decided.

## What was done this session

1. Ran the first resume-matcher POC: `cv_1000.md` (Tim Jansen's QA/test-automation CV)
   against the 1045 postings from the prior session's scrape, via `job_matcher.py --mode
   embed`. Wrote a new `resume-matcher/build_report.py` (stdlib-only) to turn the JSONL
   output into `reports/poc_cv1000_vs_scraper.{md,html}` — stat tiles, score histogram,
   per-site breakdown, top-30 table. Built following the `dataviz` skill's palette/marks
   guidance.
2. User feedback on that first report: dark mode was unreadable, and asked for a Remote
   yes/no column. Fixed dark mode (root cause: theme CSS variables were scoped to a child
   `<div class="viz-root">` instead of `:root`, so `body`'s `var(--page)`/`var(--text-primary)`
   never resolved — moved variables to `:root`). Added a Remote column using a title/location
   regex heuristic (later fully replaced — see below).
3. User asked for the "best" logit-read mode (classify/rank/category/criteria) on the
   embed-ranked jobs, capped at 10 minutes, without reloading the model. Added a
   `--time-budget` flag to `job_matcher.py` (checks elapsed wall-clock time before each
   pair, stops gracefully). Picked `category` mode per the README's own benchmarks (fastest
   correct option + only mode with a documented 28/28 ground-truth-agreement claim).
   Diagnosed a real environment bug along the way: `--gpu-layers -1` hangs indefinitely on
   this machine's llama-cpp-python build (0.3.35) — confirmed via isolated repro, worked
   around by passing the model's exact layer count (36) instead of the sentinel `-1`.
   Scored 89 pairs (top embed matches) within budget, merged into the report as a
   "Deep read: category mode" section.
4. User flagged the actual bug: Djinni's "Strong Junior\Middle General QA Engineer"
   (Ukraine, genuinely fully remote per the user's own knowledge of the posting) showed
   "Remote: No". Diagnosed: the site's remote signal was never captured by the scraper in
   the first place, so no report-layer heuristic could fix it. Agreed with the user's own
   instinct: fix belongs in the scraper (structured per-site field), plus store raw
   HTML/JSON per posting so future fields don't require re-scraping.
5. Built the pattern once on `wearedevelopers` as the reference implementation:
   - `job_scraper/core/workplace.py` — `classify_workplace(*texts)`, mutually-exclusive
     Fully Remote / Hybrid / On-site / `None` (unknown), hybrid and on-site checked before
     a bare "remote" mention so they can't collide.
   - `JobPosting.workplace` field (`job_scraper/core/models.py`), included in
     `content_hash()`; rendered as `- Workplace: ...` in `markdown_export.py`.
   - `job_scraper/core/raw_export.py` (new) + `pipeline.py` + `cli.py` — raw fetched page
     bytes saved unconditionally (before dedup/exclusion) to `raw/<site>/<file>.{html,json}`,
     on by default via `--raw-dir` (default `raw/`), opt out with `--no-raw`.
     `SiteAdapter.raw_format` ClassVar (default `"html"`) lets an adapter declare its raw
     page is JSON instead.
   - Live-verified end-to-end via a real scrape into throwaway paths before rolling out
     further.
6. Rolled the same pattern out to the other **19** site adapters via Haiku subagents, each
   independently investigating their own site's fixtures for a real per-site signal (not a
   copy-paste). Concurrency was corrected to strictly 2-at-a-time mid-rollout after
   launching too many at once; one agent (djinni's first attempt) got silently interrupted
   by that correction before writing anything and was relaunched clean. Real signals found
   varied a lot per site: JSON-LD `jobLocationType`, a `remoteInPercent` field, a Dutch
   "Werkvorm" field, a "50%-50%" split-text pattern, various Dutch phrase translations
   (hybride/thuiswerken/op locatie → English), a title suffix like "(On-site)", or
   correctly landing on `None` (unknown) when no genuine signal existed rather than
   fabricating one. Full test suite: 207 passed after all 19 (up from 188 baseline before
   this session).
7. My own review pass (not delegated) caught two problems in the delegated work:
   - `iamexpat` was scanning the full free-text job description for keywords — a real
     false-positive risk at its scale (275 postings; classify_workplace has no negation
     handling, so "not a remote position" would still match). Narrowed to location-only.
   - `working_nomads` landed on `None` for every posting because its location field is
     always just a timezone string (e.g. "Time zone: CET (+/- 3 hours)") — but the site
     is a remote-jobs-only board by definition. Added a fallback: `classify_workplace(location)
     or "Fully Remote"`.
   - Spot-checked `guru`'s diff (it also newly populated a previously-always-`None`
     `location` field via real JSON-LD data — a genuine bonus fix, not scope creep).
8. Ran a full fresh rescrape (`scrape --site all`). Along the way, found two **pre-existing**
   scraper pipeline bugs (not introduced this session, just newly consequential):
   - `apply_dedup`/`find_duplicate` (`job_scraper/core/filters.py`) matches by normalized
     title/client/location with no site/listing awareness, so re-scraping the *same*
     posting from the *same* site on a later run gets flagged a "duplicate" of its own
     prior-session DB row and **skips the markdown rewrite** — meaning the new field
     silently failed to land on anything already in `scraper.db`. Workaround used today:
     cleared `scraper.db` and `jobs/` (both gitignored, nothing lost) and rescraped fresh.
     **This will recur on the next rescrape** unless the dedup logic itself is fixed.
   - `pipeline.py`'s `run()` has no per-site exception isolation: a single transient
     network timeout on `stone_interim` crashed the *entire* 20-site batch (exit 1, zero
     sites' counters printed even though 16 had already succeeded). Recovered by
     re-running just the 5 incomplete sites in a follow-up invocation.
   - Final state after recovery: **1078 postings**, 378 with an explicit Workplace value
     (312 Fully Remote / 65 Hybrid / 1 On-site), all 20 `raw/<site>/` directories populated
     (1.1GB total, 10GB free on disk), 207 tests passing.
9. Regenerated the resume-matcher report against the fresh data. Updated
   `build_report.py` to read the scraper's real `- Workplace:` field (the `JOB_FIELD_RE`
   already captured it generically) instead of the old title/location regex guess, and
   dropped the "inferred, not verified" caveat since it's now backed by genuine per-site
   extraction. Hit a **new, unrelated bug** re-running embed mode: `RuntimeError:
   Expected all tensors to be on the same device, ... cpu and cuda:0` — root cause:
   `Embedder.embed_document()`'s cache-hit path built the tensor via bare `torch.tensor
   (cached)` (CPU), while a cache-miss builds one on CUDA; the resume file's embedding was
   a stale CPU cache-hit from an earlier run while every job embedding was a fresh CUDA
   compute. Fixed: `torch.tensor(cached, device=self.model.device)` in
   `resume-matcher/job_matcher.py`.
10. User pointed back at the **original motivating posting** (Djinni, "Strong Junior\Middle
    General QA Engineer") — still showing no Workplace value even after the full 19-site
    rollout. Root cause: djinni's fix only covered a title-suffix pattern
    ("... (On-site)"); this specific posting's real signal is a *different* structured
    field entirely — a details-list entry on djinni.co's own detail page listing every
    work arrangement the employer accepts (e.g. "Office, Remote, Hybrid Remote"), separate
    from both the JSON-LD block and the title. Fixed `job_scraper/sites/djinni.py`
    directly (`_extract_workplace_options`): matches by content against a small controlled
    vocabulary (robust against unrelated `<strong>` tags sharing the same CSS class, which
    was verified empirically, not assumed). Djinni's coverage went from 1/15 → 12/15; the
    exact flagged posting now correctly reads "Fully Remote". Added a regression test
    (`tests/test_djinni.py::test_parse_detail_workplace_options_list`) — caught and fixed a
    self-inflicted `Edit` mistake while adding it (a single-line anchor match wasn't unique
    enough and silently orphaned three assertions from an existing test into the new one;
    caught before running, fixed by hand).
11. Re-scraped just `djinni` (cleared its DB rows + markdown first, to dodge the dedup bug
    from #8), regenerated the embed match + report a final time, and screenshot-verified
    both light and dark mode render correctly with the corrected data.
12. Two `SendUserFile` attempts to show the HTML report failed both times ("this session
    is not on a project thread, so it has nowhere to place a file") — pointed to the
    on-disk path instead each time; this is a session/environment limitation, not
    something to retry differently.
